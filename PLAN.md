# Puzzle Arena — multiplayer puzzle & board game platform

## Context

Build a web app where an admin registers, hosts a game room, and players join with a 6-character passcode to play together. The host sets a time limit. Scoring rewards speed and correctness, and players who do not finish still score on partial progress. Ship six games: four concurrent puzzle games with effectively unlimited players (Sudoku, Killer Sudoku, Nonogram, Word Search) and two turn-based board games with fixed player counts and a full interactive board dashboard (Monopoly-equivalent, Cluedo-equivalent). Every game can be played solo against computer opponents that the host seats in the lobby. Puzzles are generated by an in-house constraint solver that proves a unique solution; an LLM supplies themed content only. The LLM provider is user-configurable at runtime through an admin screen, with MiniMax (`https://api.minimaxi.com/v1`, `MiniMax-M3`) as the seeded default. The entire interface commits to a retro pixel-arcade visual language, specified in full below so no screen invents its own styling.

End state: `npm run dev` serves a working platform locally against Dockerised Postgres; `npm run build` produces a single container deployable to Zeabur.

## Scoring — exact and fixed

Constants live in `packages/shared/src/scoring.ts` and are **not** host-configurable, so results are comparable across rooms.

Every game module returns the same struct:

```ts
export interface ScoreInput {
  progress: number;          // 0..1, monotonic fraction of the goal reached
  accuracy: number;          // 0..1
  completed: boolean;
  completedAtMs: number | null; // ms from room start; null unless completed
  penalties: number;         // hints, illegal-move strikes, turn timeouts
}

export const SCORE_WEIGHTS = { progress: 0.55, accuracy: 0.20, speed: 0.25 } as const;
export const PENALTY_POINTS = 15;

export function computeScore(i: ScoreInput, timeLimitMs: number): number {
  const speed = i.completed && i.completedAtMs !== null
    ? Math.max(0, (timeLimitMs - i.completedAtMs) / timeLimitMs)
    : 0;
  const raw = 1000 * (SCORE_WEIGHTS.progress * i.progress
                    + SCORE_WEIGHTS.accuracy * i.accuracy
                    + SCORE_WEIGHTS.speed    * speed)
            - PENALTY_POINTS * i.penalties;
  return Math.max(0, Math.min(1000, Math.round(raw)));
}
```

Ranking within a room: `score` desc → `completedAtMs` asc (nulls last) → `penalties` asc → `seat` asc.

Per-game `progress` / `accuracy` / `completed`:

| Game | progress | accuracy | completed |
|---|---|---|---|
| Sudoku, Killer Sudoku, Nonogram | `cellsCorrect / cellsTotal` where `cellsTotal` = cells blank at start | `cellsFilled > 0 ? cellsCorrect / cellsFilled : 1` | grid exactly equals solution |
| Word Search | `wordsFound / wordsTotal` | `wordsFound / max(1, selectionsSubmitted)` | all words found |
| Property Tycoon | `netWorth / max(1, maxNetWorthAmongLivePlayers)`; bankrupt player = `0` | `actionsAccepted / max(1, actionsSubmitted)` | player is the winner (sole solvent player, or highest net worth at expiry) |
| Manor Mystery | `cardsProvablyEliminated / 18` (own dealt cards + every card privately shown to them; 18 = 21 cards − 3 in the case file) | `1 − 0.5 × wrongAccusations`, floored at 0 | correct accusation |

Time limit is mandatory for every room (host picks it in the lobby), so `speed` always has a denominator. `penalties`: +1 per puzzle hint, +1 per rejected illegal action, +1 per auto-played turn timeout.

## Design system — retro pixel-arcade

The whole app commits to one visual language: 8-bit arcade. Dark base, hard-edged shadows with zero blur, square corners, chunky 2px borders, a pixel display font used sparingly, and stepped rather than smooth motion. **No bespoke pixel art is produced** — the retro read comes entirely from typography, colour, hard shadows, square geometry and stepped animation, so there are no sprite assets to draw. Fine detail (Sudoku digits, deed rent ladders, cash figures) uses a clean grotesk with tabular numerals, because a pixel font is unreadable at those sizes and would wreck the puzzle grids.

### Shape and depth

- Radius `0` everywhere. Borders `2px solid var(--color-pa-border)`; interactive elements get `2px solid` in their accent colour.
- Depth is a hard offset shadow, never a blur: `box-shadow: 4px 4px 0 var(--color-pa-shadow)`. On `:hover` the element moves `translate(-1px,-1px)` and the shadow grows to `5px 5px 0`; on `:active` it moves `translate(2px,2px)` and the shadow shrinks to `2px 2px 0`, so buttons physically press.
- Focus ring: `outline: 3px solid var(--color-pa-cyan); outline-offset: 2px`. Never removed.
- Disabled: `opacity: 0.45`, shadow removed, `cursor: not-allowed`.
- All spacing is a multiple of 4px (Tailwind's default scale already is).
- Page background carries a static pixel lattice: `repeating-linear-gradient` producing a 1px grid line every 8px at 4% opacity over `pa-bg`.
- A CRT scanline overlay (`repeating-linear-gradient` 2px transparent / 1px `rgba(0,0,0,0.18)`) sits above the app in a `pointer-events: none` fixed layer, toggleable in settings, default **on**, persisted to `localStorage` under `pa:crt`.
- Any raster image gets `image-rendering: pixelated`.

### Iconography

`lucide-react` rendered at 16px or 24px with `strokeWidth={3}` and CSS `shape-rendering: crispEdges`, which flattens the anti-aliasing enough to sit with the pixel type. Player tokens are a solid seat-colour square with a 2-character monogram in Press Start 2P at 8px. Manor Mystery weapons are lucide icons in the room's tint. This is a deliberate substitute for a bespoke sprite set — do not commission or draw pixel art.

### Motion

Stepped, not smooth. Use framer-motion with `transition: { type: "tween", ease: "linear" }` and quantised targets rather than easing curves:

- Board token movement animates one square at a time, 90ms per square, linear — the step *is* the retro feel and it also makes a Property Tycoon move readable.
- Dice: 6 discrete face swaps at 60ms, then settle on the server-supplied value. The face sequence is cosmetic and must never be read as the result.
- Panels and modals: no fade. They appear with a 2-frame scale snap (`scale: 0.96 → 1` over 80ms, linear).
- Progress bars are **segmented into 10 discrete blocks**, never a smooth fill.
- Countdown flips digit-by-digit; under 30 seconds it alternates `pa-ink` / `pa-danger` on a 1s beat.
- `@media (prefers-reduced-motion: reduce)`: tokens jump straight to their destination, dice show the final face immediately, panels appear with no transform. Implement as a `useReducedMotion()` guard in one `motion.ts` helper, not scattered media queries.

### Accessibility floor

Body text on `pa-bg` and `pa-surface` must clear 4.5:1 (`pa-ink` on `pa-bg` is ~14:1; `pa-ink-dim` on `pa-surface` is ~4.6:1 — do not darken it further). Accent colours are used for fills and borders, not for small text on dark. Seat identity is never colour-only: every player chip also shows its monogram, and Property Tycoon deeds show the group name as text alongside the colour bar.

### 2. `packages/shared` — wire contract, registry, scoring, PRNG

- `scoring.ts` exactly as specified above.
- `rng.ts`: `mulberry32(seed: number)` returning `{ next(): number; int(maxExclusive: number): number; shuffle<T>(a: T[]): T[]; calls: number }`. Every generator and every board-game reducer draws randomness only from this, and reducers persist `{ seed, calls }` inside game state so an event replay reproduces the game bit-for-bit. Do not use `Math.random` anywhere outside tests.
- `registry.ts`: `GAME_REGISTRY: Record<GameId, GameMeta>` with `{ id, title, kind: 'puzzle'|'board', minPlayers, maxPlayers, defaultTimeLimitSec, supportsBots: true, configSchema: ZodType }`. Player limits: `sudoku`/`killer-sudoku`/`nonogram`/`word-search` → 1–200; `property-tycoon` → 2–8; `manor-mystery` → 3–6. Default time limits: 900s puzzles, 3600s Property Tycoon, 1800s Manor Mystery. Also export `BOT_NAME_POOL` (24 fixed names, e.g. `Ada`, `Turing`, `Hopper`, `Lovelace`) and `BotDifficulty = 'easy'|'normal'|'hard'`.
- `protocol.ts`: Zod discriminated unions for every socket message, both directions (listed in step 5). Client and server both import these; every inbound payload is `safeParse`d at the handler boundary.

### 3. `packages/puzzles` — solver-backed generation

One shared core, four thin game modules. Public surface per module:

```ts
generate(opts: { difficulty: Difficulty; seed: number }): { puzzle: P; solution: S; meta: M };
grade(playerState: unknown, solution: S): { cellsTotal: number; cellsFilled: number; cellsCorrect: number; complete: boolean };
hint(puzzle: P, solution: S, playerState: unknown): HintResult;
```

- **`core/solver.ts`** — bitmask candidate solver for 9×9 Latin-square-with-boxes problems. Constraint propagation (naked single, hidden single, naked pair/triple, pointing pair, box-line reduction, X-wing) with a `countSolutions(grid, cap = 2)` DFS fallback that stops at `cap`. `rateDifficulty()` returns the highest technique tier required before any guessing: tier 1 naked single → `easy`, 2 hidden single → `easy`, 3 naked pair/triple → `medium`, 4 pointing pair / box-line → `hard`, 5 X-wing or any required guess → `expert`.
- **`sudoku.ts`** — seed a full grid by randomized backtracking with the seeded PRNG, then dig: shuffle the 81 positions, remove one at a time, restore it whenever `countSolutions(...,2) !== 1`. Stop when `rateDifficulty` hits the requested tier or the position list is exhausted; if the target tier is unreachable, retry with a fresh seed up to 20 times, then return the closest tier reached and record it in `meta.actualDifficulty`.
- **`killer-sudoku.ts`** — full grid as above; partition all 81 cells into orthogonally-connected cages of size 2–5 by randomized region growth (never repeating a digit inside a cage); cage sums come from the grid; remove **all** given digits. Verify uniqueness with the cage-sum-aware solver. On failure, split the largest cage in two and re-verify; after 10 failed splits, reveal one given digit and repeat. This always terminates because a fully-revealed grid is trivially unique.
- **`nonogram.ts`** — sizes 10×10 / 15×15 / 20×20. Fill a random binary grid at ~0.55 density biased toward runs of 2–5, derive row/column run clues, then verify uniqueness with a line-solver that iterates rows and columns to fixpoint. If the line-solver reaches fixpoint fully determined → `easy`/`medium` (by iteration count). If not, run depth-1 guessing; unique → `hard`; ambiguous → discard and regenerate with the next seed.
- **`word-search.ts`** — grid 12×12 to 18×18. Place words in 8 directions with backtracking, then fill the remainder with letters drawn from English letter frequency. After filling, re-scan the grid in all 8 directions and reject the fill if any target word appears a second time or any other target word appears at an unintended position; retry the fill up to 50 times, then regrow the grid. Word list arrives from the AI layer (step 4) with a bundled fallback.

`meta` always carries `{ actualDifficulty, generationMs, seed }`.

Tests (`packages/puzzles/*.test.ts`) are the correctness proof for this step: for each puzzle, generate 25 instances across all difficulties with fixed seeds and assert `countSolutions(...) === 1`, assert `generate` is deterministic for a given seed, and assert `grade` returns `complete: true` for the solution and `cellsCorrect === 0` for an empty board.

### 4. AI layer — pluggable providers

Every provider is treated as an OpenAI-compatible `POST {baseUrl}/chat/completions` endpoint with `Authorization: Bearer <key>`; that is all MiniMax, Zeabur AI Hub, OpenAI, OpenRouter and Anthropic-compatible gateways need.

- `apps/server/src/ai/crypto.ts` — AES-256-GCM encrypt/decrypt of provider API keys using `APP_ENCRYPTION_KEY` (32-byte base64, required env). Store `iv:tag:ciphertext` base64. Keys are never returned over HTTP; the API returns `keyLast4` only.
- `apps/server/src/ai/client.ts` — `complete({ task, system, user, schema })`. Resolves the provider via `ai_task_providers[task]` falling back to `ai_providers.is_default`. Sends `{ model, messages, temperature, max_tokens }` with `AbortSignal.timeout(provider.timeout_ms)` (default 8000). **Do not send `response_format`** — support for it is inconsistent across providers. Instead instruct JSON in the system prompt, extract the first balanced `{…}` or `[…]` from the reply, and validate with the caller's Zod schema. One retry on network error, timeout, or schema failure; on second failure return the bundled fallback and log a warning. Results are cached in `ai_content` keyed by `(task, sha256(model + system + user))`.
- Tasks: `wordsearch_theme` (returns `{ words: string[] }` — 10–18 entries, 4–9 letters, `/^[A-Z]+$/`, deduped, rejected entries dropped before the schema check), `mystery_flavour` (returns `{ victim, setting, blurb }`, purely cosmetic, never touches the solution), `puzzle_title`. Fallbacks live in `apps/server/src/ai/fallbacks.ts` with 20 hand-written themed word lists and 10 mystery blurbs.
- Seeding: on boot, if `ai_providers` is empty and `AI_BASE_URL` + `AI_API_KEY` are set, insert one enabled default row using `AI_MODEL` (default `MiniMax-M3`) and `AI_PROVIDER_NAME` (default `MiniMax`). `.env.example` ships `AI_BASE_URL=https://api.minimaxi.com/v1`, `AI_MODEL=MiniMax-M3`.
- Admin REST (all require an admin session): `GET/POST /api/admin/ai/providers`, `PATCH/DELETE /api/admin/ai/providers/:id`, `POST /api/admin/ai/providers/:id/test` → fires a 5-token completion and returns `{ ok, latencyMs, error? }`, `PUT /api/admin/ai/tasks/:task` to bind a task to a provider.

### 5. Server core — auth, rooms, socket runtime, timers

- **Fastify 5** with `@fastify/cookie`, `@fastify/rate-limit` (20 req/min on join and auth routes), `@fastify/static` serving `apps/web/dist` with SPA fallback in production. `socket.io` attaches to `app.server` after `await app.listen(...)`; no CORS config is needed because client and API share an origin.
- **Admin auth**: Better Auth with `drizzleAdapter(db, { provider: 'pg' })` and `emailAndPassword: { enabled: true }`, mounted at `/api/auth/*`. Signup is gated without relying on Better Auth hook internals: register a Fastify `preHandler` that returns 404 for `POST /api/auth/sign-up/email`, and expose our own `POST /api/admin/register` which checks `body.signupCode === process.env.ADMIN_SIGNUP_CODE` (constant-time compare) and only then calls `auth.api.signUpEmail({ body, asResponse: true })` server-side, forwarding the returned `Set-Cookie`. Sign-in, sign-out and session routes stay on the Better Auth handler untouched.
- **Guest identity**: `POST /api/guest` mints `guestId = nanoid(21)` and sets a signed, `httpOnly`, `sameSite: 'lax'`, 30-day cookie `pa_guest`. No DB row until the guest joins a room. A guest is never an auth user.
- **Room REST**: `POST /api/rooms` (admin only; body `{ gameId, config, timeLimitSec }`, validated against `GAME_REGISTRY[gameId].configSchema`) → generates a passcode from the alphabet `23456789ABCDEFGHJKMNPQRSTVWXYZ` (Crockford-style, no `0/O/1/I/L/U`), retrying on unique-index violation up to 5 times. `GET /api/rooms/:code` returns lobby metadata for the join screen. `GET /api/rooms/:id/results` returns the final table.
- **Room runtime** (`apps/server/src/rooms/runtime.ts`): a `Map<roomId, LiveRoom>` holding authoritative state in memory. `LiveRoom` owns the game state, per-player state, the event sequence counter, and one `setTimeout` armed for `endsAt`. Every mutating action appends to `room_events` and, every 50 events, writes `room_snapshots`. On boot, rooms with status `running` are rehydrated by loading the newest snapshot and replaying later events through the same reducer — which is exactly why the PRNG lives in state.
- **Timers**: the server sends absolute `endsAt` epoch-ms; the client renders its own countdown and resyncs from every snapshot. There is no per-second broadcast. The server rejects any action with `Date.now() > endsAt` and the armed `setTimeout` finalises the room. Board games additionally carry `turnTimeLimitSec` (default 90): on expiry the server auto-plays the minimal legal action (roll, or end turn) and adds one penalty.
- **Disconnect**: a player keeps their seat for `reconnectGraceSec` (120). Puzzle progress simply freezes. In a board game, if it becomes a disconnected player's turn, the turn timer is skipped and the minimal legal action fires immediately.
- **Socket auth middleware**: `io.use` reads `socket.handshake.headers.cookie`; an admin session (via `auth.api.getSession`) sets `socket.data.userId`, otherwise the signed `pa_guest` cookie sets `socket.data.guestId`. Missing both → reject.

Wire protocol (all defined in `packages/shared/src/protocol.ts`):

*Client → server:* `room:join {code, displayName}` (ack `{snapshot}`), `room:leave`, `room:start` (host only), `room:kick {playerId}` (host only), `puzzle:commit {path, value}` (ack `{accepted, correct?, progress}`), `puzzle:hint` (ack `{hint}`), `game:action {…}` (per-game discriminated union, ack `{accepted, error?}`), `chat:send {text}`.

*Server → client:* `room:snapshot {room, players, you, state, endsAt}`, `room:players`, `room:started {startsAt, endsAt}` (`startsAt` is ~2200ms in the future so every client runs the 3·2·1·GO overlay in step and play begins simultaneously), `room:ended {results}`, `leaderboard {entries}`, `game:state {publicState, privateState}`, `game:log {entries}`, `chat:message`, `error {code, message}`.

**Anti-cheat invariants, non-negotiable:** the solution never leaves the server; `puzzle:commit` returns `correct` only when the host enabled `instantFeedback` (default **off**); the broadcast leaderboard carries `filledFraction`, never `correctFraction`, while feedback is off; `game:state.privateState` is computed per-socket by the engine's `view(state, playerId)` and a spectator gets `view(state, null)`.

### 6. Turn-based engine contract + Property Tycoon

`packages/games/src/engine.ts`:

```ts
export interface GameEngine<S, A> {
  id: GameId;
  setup(playerIds: string[], seed: number, config: unknown): S;
  reduce(s: S, playerId: string, action: A): { ok: true; state: S; log: LogEntry[] } | { ok: false; error: string };
  autoAction(s: S, playerId: string): A;      // played on turn-timeout / disconnect
  view(s: S, playerId: string | null): unknown;
  score(s: S, playerId: string): ScoreInput;
  isOver(s: S): { over: boolean; winner?: string };
}
```

`reduce` is pure; all randomness comes from `s.rng` (`{ seed, calls }`) advanced inside the returned state.

**Property Tycoon** (`packages/games/src/property-tycoon/`), 2–8 players. Economically identical to the classic game, with all names replaced so no trademark is used. Rent tables, prices and mortgage values are in the reference table below and must be copied verbatim into `board.ts`.

Turn state machine — `phase` field on state:
`awaiting_roll` → `resolving_square` → one of `awaiting_purchase_decision` / `auction` / `awaiting_debt_settlement` / `awaiting_end_turn`; `in_jail_decision` replaces `awaiting_roll` while jailed.

Actions: `roll`, `buy`, `decline`, `bid {amount}`, `passBid`, `buildHouse {propertyId}`, `sellHouse {propertyId}`, `mortgage {propertyId}`, `unmortgage {propertyId}`, `proposeTrade {toPlayerId, give, receive}`, `respondTrade {tradeId, accept}`, `payJailFine`, `useJailCard`, `declareBankruptcy`, `endTurn`.

Rules that must be implemented exactly:
- $1500 start (configurable), $200 on landing on or passing START. A card that says "Advance to START" pays $200 once; no double payment for a card whose path crosses START.
- Full-colour-group ownership with no houses doubles the base site rent.
- Transit line rent by count owned: 25 / 50 / 100 / 200. Utility rent: 4× dice total with one owned, 10× with both.
- Even build within a colour group in both directions; 4 houses then hotel; bank supply capped at **32 houses and 12 hotels**, and a build is rejected when the bank is empty.
- Mortgage = half price; no rent on a mortgaged property; unmortgage costs mortgage + 10%. Houses in a group must be sold back (half price, evenly) before any property in it can be mortgaged.
- Jail: enter via the Go To Jail square, the card, or three consecutive doubles (the third roll is not moved). Exit by paying $50, using a card, or rolling doubles (no extra turn for that double). On the third failed turn, pay $50 and move the third roll. Rent, trading and building all continue while jailed.
- Revenue Levy: player chooses $200 or 10% of net worth (cash + face value of unmortgaged property + mortgage value of mortgaged property + half building cost). Luxury Levy: flat $75.
- Declining an unowned property triggers an immediate auction, minimum bid $1, open to every solvent player including the decliner. Enabled by default; host may disable it in room config.
- Rest Stop does nothing (the jackpot variant is a host-toggleable option, default off).
- Bankruptcy to a player transfers cash, deeds and jail cards, with buildings sold to the bank first; bankruptcy to the bank re-auctions the deeds. The player retires and scores `progress = 0`.

**Manor Mystery** is step 7; do not start it until Property Tycoon's reducer tests pass.

### 7. Manor Mystery (Cluedo-equivalent)

`packages/games/src/manor-mystery/`, 3–6 players. Rooms and weapons keep their generic English names; the six suspects are renamed because the originals are distinctive marks.

- Suspects: **Ms. Crimson** (red), **Major Ochre** (yellow), **Mrs. Ivory** (white), **Mr. Verde** (green), **Lady Azure** (blue), **Dr. Mauve** (purple).
- Weapons: Candlestick, Dagger, Lead Pipe, Revolver, Rope, Wrench.
- Rooms: Kitchen, Ballroom, Conservatory, Dining Room, Library, Billiard Room, Lounge, Hall, Study.

**Board geometry** — a 24×24 grid, generated from these bands, not hand-drawn. Room rectangles are inclusive:

| | cols 1–6 | cols 9–14 | cols 17–22 |
|---|---|---|---|
| **rows 1–6** | Kitchen | Ballroom | Conservatory |
| **rows 9–14** | Dining Room | Library | Billiard Room |
| **rows 17–22** | Lounge | Hall | Study |

Every cell not inside a room rectangle is a corridor cell (columns 0, 7, 8, 15, 16, 23 and rows 0, 7, 8, 15, 16, 23). Each room has exactly **two doors**, derived by rule so the layout is generated rather than hand-drawn. A door is a room-edge cell paired with the adjacent corridor cell; movement may cross only at a door.

- Horizontal door edge: rooms in the **left** column band (cols 1–6) use their **right** edge (x = 6, opening to x = 7); rooms in the **centre** band (cols 9–14) also use their **right** edge (x = 14, opening to x = 15); rooms in the **right** band (cols 17–22) use their **left** edge (x = 17, opening to x = 16).
- Vertical door edge: rooms in the **top** row band (rows 1–6) use their **bottom** edge (y = 6, opening to y = 7); rooms in the **centre** band (rows 9–14) also use their **bottom** edge (y = 14, opening to y = 15); rooms in the **bottom** band (rows 17–22) use their **top** edge (y = 17, opening to y = 16).
- Each door sits at offset 3 along its edge within the room's 6-cell span — so a room spanning 1–6 puts its door at coordinate 4 on that axis.

Worked example (Kitchen, cols 1–6 × rows 1–6): right door at room cell `(6,4)` opening to corridor `(7,4)`; bottom door at room cell `(4,6)` opening to corridor `(4,7)`.

Secret passages connect the diagonally opposite corner rooms: **Kitchen ↔ Study** and **Conservatory ↔ Lounge**. There is no cellar square — the case file is a UI element, not a board square.

Start squares: walk the outer corridor ring clockwise from `(0,0)` (perimeter length `4 × 24 − 4 = 92`). Suspect `k` (0-indexed in the order Crimson, Ochre, Ivory, Verde, Azure, Mauve) starts at perimeter index `Math.floor(k * 92 / 6)` → indices 0, 15, 30, 46, 61, 76.

Mechanics:
- 21 cards (6 + 6 + 9). One suspect, one weapon, one room go to the case file; the remaining 18 are dealt round-robin, so hands are uneven with 4 or 5 players. The deal order is drawn from the seeded PRNG.
- Turn: `awaiting_action` → `roll` (2d6) or `useSecretPassage` (corner rooms only, instead of rolling) or `accuse`. After rolling, the server computes reachable cells by BFS over corridor cells at exactly the rolled distance, plus any room whose door is reachable within the roll; entering a room ends movement. The client shows the reachable set and the player picks a destination.
- In a room the player may `suggest {suspect, weapon}` (the room is implied). The named suspect token and weapon move into that room. Suggesting does not end the turn.
- Refutation proceeds clockwise from the suggester. The first player holding any named card **must** show one; the choice of which card is theirs. The server sends the revealed card only to the suggester and broadcasts a public log line naming who refuted, never what. If nobody can refute, the log says so.
- `accuse {suspect, weapon, room}` can be made on your turn instead of moving. Correct → immediate win. Wrong → the player is locked out of moving, suggesting and accusing but must keep refuting others; their state records `wrongAccusations += 1`.
- `view(state, playerId)` exposes: full board, all token positions, the public log, each player's hand **size**, and the requesting player's own hand plus their private revelation history. It must never contain the case file or another player's cards. `view(state, null)` for spectators drops all hands and all revelations.
- Server-side notepad: the engine maintains `eliminated: Set<CardId>` per player (own cards ∪ cards shown to them) — this is what drives `progress = |eliminated| / 18` and it is also pushed to the client to prefill the notepad. The client notepad additionally stores free-form tri-state marks locally per player.

### 8. Computer players (bots)

So a solo host can play any of the six games alone. Bots take real seats, appear on the leaderboard, and are scored through the identical `computeScore` path as humans — no special-casing in step 14.

**Seating.** Host adds and removes bots in the lobby: `POST /api/rooms/:id/bots {difficulty}` and `DELETE /api/rooms/:id/bots/:playerId`, both host-only and both rejected once `status !== 'lobby'`. A bot row has `guest_id = NULL`, `is_bot = true`, and a name taken from `BOT_NAME_POOL` (first unused). Start is permitted when `humans >= 1` and `humans + bots >= GAME_REGISTRY[gameId].minPlayers`; `maxPlayers` counts bots. In practice: puzzles need no bots, Property Tycoon solo needs ≥ 1, Manor Mystery solo needs ≥ 2.

**No-cheat invariant — the thing most likely to be got wrong.** A bot policy is a pure function of *exactly* the restricted view a human in that seat would receive:

```ts
export interface BotPolicy<V, A> {
  chooseAction(view: V, selfId: string, rng: Rng, difficulty: BotDifficulty): A;
}
```

The runtime calls `engine.view(state, botPlayerId)` and passes only the result. Each game's `bot.ts` must not import its own state type `S` — the module boundary is the enforcement. A test asserts that the object handed to `chooseAction` contains neither the Manor Mystery case file nor any other player's card ids.

**Scheduler** (`apps/server/src/rooms/bots.ts`). After every state transition the runtime checks whether the seat now to act is a bot; if so it arms `setTimeout(500 + rng.int(1200))` (overridden to `0` by `BOT_THINK_MS=0` in tests) and then applies the chosen action through the same `reduce` → append-to-`room_events` path a human action takes. The delay is presentation only and must never feed the policy — only the seeded `Rng` may — otherwise replay stops being deterministic. Guard: after 200 consecutive bot actions in one room the runtime forces `endTurn` and logs an error, so an engine bug is loud instead of a hang.

**Property Tycoon policy.** Heuristic, with `reserve` = easy 0 / normal 150 / hard 250:
- Buy when `cash − price >= reserve`, or unconditionally when the purchase completes a colour group and `cash >= price`.
- Auction: valuation = `price × m`, where `m` = 1.6 if it completes a group for the bot, 1.25 if it would complete a group for someone else (blocking), else 0.85 (easy: 0.7). Bid in +10 steps while `bid + 10 <= min(valuation, cash − reserve)`; otherwise pass.
- Build when the group is complete and `cash − houseCost >= reserve`, evenly within the group, preferring the group with the highest `Σ rent(1 house) / Σ house cost`; hard bots break ties toward orange and red.
- Jail: pay the fine or use a card while ≥ 4 unowned streets remain; otherwise sit out the three turns.
- Debt: sell houses evenly, then mortgage the lowest-priced properties outside completed groups, then declare bankruptcy only if the shortfall remains.
- Trades: accept when `Σ value(receive) + cashIn − Σ value(give) − cashOut > 0`, where `value = price × (1.6 if that deed completes a group for the receiving side, else 1.0)`. Hard bots additionally propose at most one trade per turn that completes a group for them, offering `1.4 × price` in cash. Easy bots never build, never trade, and buy only when `cash >= price`.

**Manor Mystery policy.** Genuine deduction from the restricted view:
- Knowledge state: `eliminated` (own cards ∪ cards privately shown to it); disjunctive constraints `(playerId, {suspect, weapon, room})` recorded whenever that player refuted *someone else's* suggestion; and `notHeld(playerId, card)` for every card in a suggestion that a player declined to refute.
- Propagate to fixpoint: if two cards of a disjunction are `notHeld` by that player, they hold the third → add it to `eliminated`; a card known held by anyone is `notHeld` by everyone else.
- Candidates per type = cards of that type not in `eliminated`. Accuse the moment all three types have exactly one candidate. Hard bots also accuse when the product of the three candidate counts is ≤ 2 and the room clock is under 10% remaining. Easy and normal bots never guess.
- Movement: BFS toward the nearest room that is still a candidate, taking a secret passage when it lands closer. Suggest the candidate suspect and weapon appearing in the fewest resolved constraints (highest expected information); easy bots pick uniformly among candidates.
- Refuting: shows whichever matching card it has already revealed most often, minimising leaked information; easy bots pick at random.

**Puzzle bots.** A bot is a simulated solver sharing the same leaderboard:
- At room start the runtime replays `core/solver.ts` over the generated puzzle and records the order in which cells fall to successively harder technique tiers. That ordering is the bot's human-plausible solve path. (Word Search bots use word order by length descending.)
- The bot is assigned `targetMs = timeLimitMs × f` with `f` = easy 1.8 (so it deliberately never finishes), normal 0.95, hard 0.6, and commits one cell every `targetMs / cellsTotal`. Error rate = easy 0.08, normal 0.04, hard 0.01; an error writes a wrong but locally-legal digit which the bot overwrites with the correct one after three intervals.
- Bot commits go through the same `puzzle:commit` handler as a human's, so progress, accuracy, penalties and final score are computed by the identical code path.

**Client.** The lobby lists bot seats with a robot glyph, a difficulty `<select>`, and a remove button, all visible only to the host. In play, bots render exactly like human players apart from the glyph, and the turn indicator reads "thinking…" during the scheduler delay.

### 11. Puzzle UIs

### 14. Room finalisation and results

On completion (all puzzle players solved, board game winner decided, host ends early, or `endsAt` fires): the runtime freezes the room, calls each game's `score()`, runs `computeScore`, ranks, writes `room_results`, sets `rooms.status = 'finished'`, emits `room:ended {results}`, and clears the `LiveRoom` from memory after a 60-second grace so late clients still get the snapshot.

Results screen: podium, full table with score / progress / accuracy / speed / penalties / finish time, and for puzzles a reveal of the solution grid — which is the only moment the solution is ever sent to a client.

## Critical files & anchors

| File | Why it is the crux |
|---|---|
| `packages/shared/src/scoring.ts` | Single definition of `computeScore` and `ScoreInput`; every game feeds it, and the whole speed/correctness/partial-credit requirement lives here. |
| `packages/shared/src/rng.ts` | `mulberry32` is the only randomness source. Reducers store `{seed, calls}` in state — this is what makes `room_events` replay deterministic, so crash recovery depends on it. |
| `packages/puzzles/src/core/solver.ts` | `countSolutions(grid, cap)` and `rateDifficulty()` back the uniqueness guarantee and the difficulty tiers for three of the four puzzles. |
| `apps/server/src/rooms/runtime.ts` | `LiveRoom` owns authoritative state, the `endsAt` timeout, event append, snapshotting and rehydration. Every anti-cheat invariant is enforced here. |
| `apps/server/src/ai/client.ts` | Provider resolution, the deliberate absence of `response_format`, retry, cache and fallback. Adding a provider must require zero code changes. |
| `apps/server/src/rooms/bots.ts` | Bot scheduler. Two easy mistakes live here: handing a policy the raw state instead of `engine.view(state, botId)`, and letting the think-delay influence the chosen action, which breaks replay determinism. |

## Verification

Prerequisites: `PLAN.md` exists at the repo root (step 0). Then `docker compose up -d` for Postgres, `cp .env.example .env` and fill `DATABASE_URL=postgres://postgres:postgres@localhost:5432/puzzlearena`, `BETTER_AUTH_SECRET`, `COOKIE_SECRET`, `APP_ENCRYPTION_KEY` (`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`), `ADMIN_SIGNUP_CODE=letmein`, and the MiniMax values. Then `npm ci && npm run db:migrate && npm run dev`.

**1. Generator correctness (the hard guarantee).** `npx vitest run packages/puzzles`. Must prove, for 25 seeded instances per difficulty per puzzle: exactly one solution (`countSolutions(puzzle, 2) === 1`), determinism (same seed → identical output), and that a Killer Sudoku puzzle has no revealed digits in the common case. This is the check that distinguishes solver-backed generation from guessing.

**2. Scoring behaviour.** `npx vitest run packages/shared`. Concrete assertions: a player finishing at half the time limit with a perfect grid scores `1000*(0.55 + 0.20 + 0.25*0.5) = 875`; a player at 60% progress with 60 correct of 66 filled and no finish scores `round(1000*(0.55*0.6 + 0.20*0.909)) = 512`; two hints drop that to 482; scores clamp to `[0,1000]`.

**3. End-to-end puzzle room (manual, two browsers).** Sign up at `/admin/signup` with the signup code, create a Sudoku room with difficulty `medium` and a 5-minute limit, open `/r/:code` in a second browser profile as a guest, join with a name, host clicks Start. Confirm: both boards show the identical puzzle; entering a digit does **not** reveal correctness (feedback off); the leaderboard shows the other player's filled fraction rising; the countdown matches on both; solving the grid ends that player's run and shows their finish time. **4. Anti-cheat spot-check.** With the room running, in DevTools run `socket.onAny(console.log)` and inspect every frame plus the `room:snapshot` payload. ## Assumptions & contingencies

- **Trademark safety.** Monopoly and Cluedo are active Hasbro marks, so the two board games ship as Property Tycoon and Manor Mystery with all distinctive names replaced (board squares, card decks, suspects). Rent numbers, board order and rules are mechanics and are reproduced exactly. Room names and weapon names stay generic English nouns. If you would rather use the original names, that is a legal call to make explicitly — the rename is confined to `board.ts` and `cards.ts` in each game package.
- **TypeScript 6.0.3.** If `drizzle-kit` or `better-auth` type definitions fail to parse under 6.0.3, move the root to `typescript@7.0.2` rather than downgrading to 5.9 — 7.0.2 is the current `latest`.
- **Difficulty targets.** Sudoku `expert` may be unreachable for some seeds; the generator retries 20 seeds then returns the closest tier and records `meta.actualDifficulty`. Surface that value in the room lobby rather than failing room creation.
- **Single server process.** Room state is in memory, so there is exactly one server instance. If you later need two, the change is `io.adapter(createAdapter(pool))` with `@socket.io/postgres-adapter@0.5.0` plus moving `LiveRoom` ownership behind a per-room lock — do not design for it now.
- **MiniMax region.** The plan uses the `api.minimaxi.com` base URL as given. The global endpoint is `api.minimax.io/v1`; if requests 404, switch the provider row's base URL in `/admin/ai` — no redeploy needed, which is the point of the provider table.
- **Nonogram uniqueness cost.** If 20×20 generation exceeds ~2s, cap the size at 15×15 and generate 20×20 in a background job at room creation with a lobby spinner, rather than relaxing the uniqueness check.
- **Engagement extras are deliberately out.** Sound effects, confetti, live emote reactions and bespoke touch-gesture handling are **not** built. Seat colour + avatar identity **is** built, because Property Tycoon and Manor Mystery tokens must be distinguishable on the board — it is a functional requirement, not decoration. Layouts are responsive to 360px but there is no pinch-zoom, pan, or drag-gesture layer. If you want any of the extras later, each is contained: sounds = `howler@2.2.4` with one preloaded sprite plus a mute toggle in the existing settings popover; confetti = `canvas-confetti@1.9.4` fired from the results screen and the solve handler; emotes = one `chat:emote` socket event plus a floating layer over the board.
- **Pixel styling versus fine detail.** The retro direction fights small type, which is why Press Start 2P is capped at headings and labels while Sudoku digits, deed rent ladders and cash figures use Space Grotesk with tabular numerals. If a reviewer asks for pixel type in the grids, push back: it drops digit legibility below usable at 20px. The escape hatch, if it is insisted on, is `@fontsource-variable/pixelify-sans@5.3.0`, which is a pixel face with real lowercase and far better small-size legibility than Press Start 2P.
